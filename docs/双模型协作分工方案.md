# 双模型协作分工方案

> 适用工作区：DeepSeek Harness 一键更新方案
> 现状基线：`README.md` 1169 行（设计）、`prototype.html` 1895 行 / 17 个状态（原型）、`src/` 15 个模块约 2600 行（参考实现）、`test/` 7 个文件 58 个用例（当前全绿）
> 版本：1.0 · 2026-11-08

---

## 0. 三条前提

后面所有分工都是从这三条推出来的，任一条不成立就要重排：

1. **两个模型之间没有共享上下文。** 唯一可靠的传递介质是工作区里的文件和命令输出。所以任务必须切成"能落成文件、能跑出结果"的单元，而不是"一起讨论一下这个设计"。
2. **角色按能力轴分配，不按偏好。** 本方案假设 Kimi-K3.1-Pro 在长上下文与结构化推理上更强，DeepSeek-V4.1-Flash 在延迟和单次成本上更优。若实测与此相反，把第 1 节两列对调即可，第 2–8 节的编排骨架不变。
3. **实现者不定义"正确"。** 验收标准必须由没写这段代码的一方给出，否则测试会跟着 bug 一起长歪。

## 1. 角色定位

### 1.1 Kimi-K3.1-Pro：契约与终审

一次能读完 1169 行 README + 15 个源文件 + 7 个测试文件，做跨文件的一致性判断——这是它在这个工作区最不可替代的地方。

| 职责 | 落在哪些文件 |
|---|---|
| 需求边界：哪些做、哪些明确不做 | `README.md` §1.4 目标与非目标 |
| 不变量：17 个按钮状态的合法迁移、`prepared → applying → verifying → committed` 与回滚旁路、错误码 UPD-101…UPD-702 的阶段归属 | §4.2 状态机、§7.2 Journal、§8.3 错误码表 |
| 接口签名：`UpdateBackend` / `PluginGate` / `UpdateOrchestrator` | §10.2 |
| 失败语义：哪些阶段失败必须回滚、哪些必须零改动、哪些进安全模式 | §7.4 回滚触发条件 |
| 终审：跨模块一致性、安全项（sha512、`allowBuilds`、loopback、防降级） | §9、`src/backends/npm.mjs` |

**不该交给它**：批量产出重复度高的代码、逐条校对 8 种语言文案、连续十几轮跑测试收敛小错。

### 1.2 DeepSeek-V4.1-Flash：实现与验证

| 职责 | 说明 |
|---|---|
| 按契约卡实现模块 | 输入是契约卡 + 相关源文件，不是全量 README |
| 写测试与故障注入 | 用 `fake.mjs` 的 `failAt`（`check`/`download`/`verify`/`prepare`/`drain`/`activate`/`health`/`rollback`）覆盖失败路径 |
| 机械重构、批量文案、格式统一 | 8 语言 i18n、术语一致性 |
| 跑 `npm test` 与 7 个 demo scenario | 把失败收敛成最小复现 |
| 产出变更包 | 见 §4.2 |

**不该交给它**：单方面改状态机、错误码、接口签名——那是契约变更，必须回流到 K3.1-Pro。

## 2. 任务拆分：以"契约切片"为单位

切片 = 一次契约冻结到验收通过的最小闭环。**按契约面切，不按文件切**；按文件切会让每个切片都横跨契约与实现，验收边界就没了。

| 阶段 | 执行 | 输入 | 产出 | 门禁 |
|---|---|---|---|---|
| S1 契约冻结 | K3.1-Pro | README 对应章节 | 契约卡 | 签名、不变量、错误码、禁止事项、验收命令五件齐全 |
| S2 实现 | Flash | 契约卡 + 相关源文件 | 代码 | 能跑 |
| S3 自测 | Flash | 契约卡的验收命令 | 测试 + 场景输出 | `npm test` 全绿 |
| S4 交叉验收 | K3.1-Pro | 变更包 + 全量代码 | 验收单 | 每条不变量都有断言；边界用例通过 |
| S5 回修 | Flash | 验收单的点名项 | 增量 diff | 改动不超出点名项 |

映射到本工作区的模块，按契约浓度排：

| 模块 | 规模 | 契约 | 实现 | 验收强度 |
|---|---|---|---|---|
| `src/orchestrator.mjs` | 706 行 | K3.1-Pro | Flash | 高：失败分支逐条读 |
| `src/journal.mjs` / `src/watchdog.mjs` | 179 / 124 行 | K3.1-Pro | Flash | 高：状态迁移表逐格核对 |
| `src/plugin-gate.mjs` | 336 行 | K3.1-Pro | Flash | 高：6 条优先级规则，顺序错一位结果就变 |
| `src/backends/npm.mjs` | 496 行 | K3.1-Pro | Flash | 高：完整性、`allowBuilds`、防降级逐行审 |
| `src/semver.mjs` | 311 行 | — | Flash | 低：抽查 prerelease、`workspace:`、部分版本边界 |
| `src/i18n.mjs` / `src/telemetry.mjs` | 391 / 133 行 | — | Flash | 低：只审"是否泄漏插件名与配置值" |
| `src/backends/fake.mjs` | 191 行 | — | Flash | 低 |
| `test/*.mjs` | 7 文件 / 58 例 | Flash | Flash | K3.1-Pro 只增边界用例，不删 Flash 的用例 |
| `prototype.html` | 1895 行 / 17 状态 | Flash | Flash | 低：只验状态覆盖与 §4.2 表一致 |
| `README.md` | 1169 行 | K3.1-Pro | K3.1-Pro | Flash 只做"把实现变更回填到表格与版本记录" |

## 3. 文件所有权

同一时刻只有一个模型能改一个文件，否则合并冲突会吃掉并行收益。

| 文件 | 写权限 | 冲突处理 |
|---|---|---|
| `README.md` | K3.1-Pro | Flash 仅在"回填"任务中改指定段落，且需先报段落范围 |
| orchestrator / journal / watchdog / plugin-gate | Flash 写，K3.1-Pro 有 veto | K3.1-Pro 的修改以"批注 + 补充用例"表达，不直接改代码 |
| semver / i18n / telemetry / fake / prototype | Flash | K3.1-Pro 只读 |
| npm backend | Flash | 涉及签名、完整性、降级的改动需 K3.1-Pro 预批 |
| `test/` | Flash | K3.1-Pro 只增不删 |

## 4. 衔接协议：三种交接物

口头说"改好了"在这个流程里不算交付。三个固定格式的交接物是全部协作的接口。

### 4.1 契约卡（K3.1-Pro → Flash）

固定五段，缺一段不进入实现：

```
模块：src/plugin-gate.mjs
签名：plan(targetCore, plugins, available) → { items[], updates, keeps, disables, blocks, manuals }

不变量：
  1. 声明 engines.dsh 的插件只由该范围决定，忽略 peerDependencies
  2. 两者都未声明 → status 'unknown'，不阻断，标记 verify:false + reason:'verified-in-staging'，必须走 staging 自检
  3. 空范围 / 非法范围 / engines.dsh 里的 workspace: → 视为不兼容
  4. @deepseek-ai/* 与 core 行永不进入 disable

错误码：范围不匹配 → UPD-201（软阻断）；核心行不兼容 → UPD-202（硬阻断）

禁止：不得在本模块内读写文件；不得自行决定"禁用"如何落盘（那是 patch 层的事）

验收：npm test -- --test-name-pattern "plugin gate"
```

要点：契约卡要短到能一屏读完。写成一页半，说明切片本身该拆了。

### 4.2 变更包（Flash → K3.1-Pro）

- diff（只含本切片）
- 新增/修改的测试清单
- `npm test` 输出尾部的计数（`# pass` / `# fail`）
- 相关 scenario 的退出码（README 第 48 行：0 成功 / 1 失败 / 2 阻断 / 3 安全模式）
- **已知未解问题**：明确写出"我没把握的三处"。留空视为未完成，不是"没问题"
- **主动声明的偏差**：实现与契约卡不一致的地方，以及为什么

### 4.3 验收单（K3.1-Pro → 基线）

- 逐条不变量判定：有断言 / 无断言 / 断言写错
- 边界用例结果（K3.1-Pro 自己出的题）
- 与 README 的偏差清单（文档漂移也是缺陷）
- 结论：合入 / 带风险合入 / 退回（点名项 ≤ 5 条，逐条可判定）

## 5. 汇总与校验

三道闸门，顺序不能换。跳过任何一道，后面都会用返工补回来。

**闸门 1 · 机器校验（Flash 自跑）**

`npm test` 58 例全绿；7 个 demo scenario 退出码符合约定；`node src/cli.mjs status --home <dir>` 能读回 journal。

**闸门 2 · 契约校验（K3.1-Pro）**

每条不变量必须能在测试里找到对应断言——"实现了但没测"按未实现处理。同时核对错误码：新增或改动的码是否落在 §8.3 的阶段归属里，预检内部码（`E_DISK` / `E_BUSY` / `E_INTEGRITY`…）是否仍只写日志、不直接展示。

**闸门 3 · 对抗校验（K3.1-Pro 出题，Flash 执行）**

从 §10.3 故障注入矩阵抽查 3–5 条：sha512 错误、磁盘满、端口占用、回滚中崩溃、插件 import 失败。**预期结果由 K3.1-Pro 写死，Flash 只负责让它发生。** 这是全流程最容易被跳过、也最容易抓出真问题的一步。

汇总产物是一张验收表：

| 切片 | 状态 | 未覆盖项 | 文档偏差 |
|---|---|---|---|
| 例：npm 完整性校验失败 | 带风险合入 | 代理环境重定向未验证 | 无 |

它替代"我们改完了"这种口头结论。

## 6. 任务类型路由

| 任务类型 | 主 | 辅 | 分工要点 |
|---|---|---|---|
| 选型与取舍（§2 调研、§3 组合式方案） | K3.1-Pro | Flash | Flash 只做事实核对：star 数、周下载量、许可证、最后提交时间 |
| 新模块从零实现 | K3.1-Pro 定契约 | Flash 实现 | 契约卡超一页就先拆切片 |
| 修 bug | Flash | K3.1-Pro | Flash 先复现；30 分钟定位不到就升级，让它看全局 |

| 回滚路径 / 安全项 / 供应链 | K3.1-Pro | Flash | Flash 只实现，不改设计 |

| 原型 UI / 状态可视化 | Flash | K3.1-Pro | K3.1-Pro 只对 §4.2 的 17 状态表 |

## 7. 资源约束下的调整

| 约束 | 调整 | 代价与补偿 |
|---|---|---|
| 预算紧 | K3.1-Pro 只保留"冻结 + 终审"两个接触点，中间全交 Flash，契约卡写到函数级 | 返工率上升 → 强制每个切片带故障注入用例 |
| 时间紧 | 并行：K3.1-Pro 写下一张契约卡，Flash 实现当前切片 | **同一时刻只能有一个切片在验收**，否则回归无法定位 |
| 质量优先（发版前、动回滚路径） | K3.1-Pro 亲自写失败分支与状态迁移，Flash 退化为跑测试出报告 | 慢 40% 左右，换回滚路径可审计 |
| K3.1-Pro 不可用 | 冻结契约；Flash 只做"不改契约的测试补充"和机械改动 | 积压的契约变更排队，禁止改状态机 |
| Flash 不可用 | K3.1-Pro 全包，切片粒度减半 | 成本上升，但上下文连续性更好 |

一句话：**约束收紧时先减切片数量，不要减验收环节。**

## 8. 度量与校准

| 指标 | 定义 | 健康区间 |
|---|---|---|
| 切片一次通过率 | Flash 交付后无需退回的比例 | 60–80%；高于 90% 说明验收太松 |
| 缺陷逃逸率 | 验收后仍被发现的问题占比 | < 10% |
| 回修扩散度 | 回修时改动的非点名文件数 | 0 |
| 单切片成本 | token + 墙钟时间 | 基线 ±30% |

每 2–3 个切片复盘一次。某类任务连续两次被退回，不要"再试一次"：要么把这类契约卡写细，要么直接换主责。

## 9. 走查：一个切片跑完全程

任务：npm 后端在完整性校验失败时不得污染 staging。

1. **契约卡（K3.1-Pro）**
   - 签名：`prepare()` 在 `dist.integrity` 不匹配时抛 `UpdateError('UPD-402')`
   - 不变量：journal 停在 `prepared`；`updates/<planId>/packages` 被清理；不得进入 `applying`
   - 禁止：不得把错误降级成 warning；不得复用已下载的部分文件
   - 验收：`npm test -- --test-name-pattern integrity`
2. **实现 + 自测（Flash）**：三个用例——hash 正确、hash 错误、registry 未返回 integrity 字段
3. **变更包（Flash）**：diff + 3 个用例 + 输出计数 + 已知未解："代理环境下的重定向未验证"
4. **交叉验收（K3.1-Pro）**：检查错误是否被 `asUpdateError` 兜底成 UPD-501；补一条"下载中断后 staging 残留"的对抗用例
5. **回修（Flash）**：只改点名项。若发现契约卡本身有漏洞，退回 S1，不自行发挥

## 10. 反模式

- 两个模型同时改同一文件——冲突成本高于并行收益
- 让 Flash 先读 1169 行 README 再动手——上下文被稀释，关键约束反而丢
- 用"看起来对了"代替断言——闸门 2 的全部意义就是拒绝这种交付
- 让实现者写预期结果——测试会跟着实现走，等于没测
- 退回时不给点名项、只说"再改改"——Flash 会扩大改动面，扩散度直接失控
