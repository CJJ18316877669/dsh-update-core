# 契约

## 一句话

**契约只写"对外承诺什么"，不写"内部怎么做"。它的唯一用途是：让人或另一个模型不看你的代码，也能判断你做对了没有。**

插头怎么做随便，但尺寸和电压必须一致。契约就是那个尺寸和电压。

## 它不是什么

- 不是设计文档：设计文档写"为什么这么选"，可以有取舍、有争论、有历史。
- 不是代码：代码是实现，随时可以改，改完只要契约还成立就不算破坏。
- 不是需求：需求是"我要能更新"，契约是"更新失败时必须回到旧版本，且旧版本可启动"。

## 契约的四要素

| 要素 | 回答 | 少了会怎样 |
|---|---|---|
| 签名 | 怎么调用，输入输出是什么 | 别人接不上，只能读代码猜 |
| 不变量 | 什么绝对不能破 | 实现"看起来能跑"，但边界一碰就碎 |
| 错误归属 | 出错算哪种错、哪个阶段 | 同一个故障在不同模块报不同码，用户看不懂 |
| 验收 | 用什么命令、什么输出算做完 | 无法判断完成度，只能靠感觉 |

## 三层契约

| 层 | 内容 | 落在哪 | 谁改 |
|---|---|---|---|
| 接口契约 | `UpdateBackend` 的 11 个方法、`PluginGate` 的 `disable/restore`、store 的 `disable/enable` | `README.md` §10.2、各模块 JSDoc | 主模型 |
| 行为契约 | 17 个状态名、`ALLOWED_TRANSITIONS`、退出码 0/1/2/3、取消边界 | `src/journal.mjs`、`src/cli.mjs` | 主模型 |
| 任务契约 | 单个切片做什么、不许做什么、怎么算完 | 本目录的 `C-00x-*.md` | 主模型定，副模型执行 |

改接口契约或行为契约 = 破坏性变更，公开发布后必须发 major 并写迁移说明。
改任务契约 = 正常迭代，卡片本身就可以改。

## 卡片模板

```markdown
# C-00x 标题

状态：待实现 / 实现中 / 待验收 / 已合入
依赖：<前置卡片>
阻塞：<后续卡片>

## 现状
一两句，说清现在为什么不行。带文件与行号。

## 对外接口
签名，代码块。

## 不变量
编号列表，每条都必须可判定（能写成断言，或能用一个命令验证）。

## 待确认
实现前必须先回答的问题。答不出来就先别写代码。

## 禁止
越界即退回，不讨论。

## 验收
命令 + 期望输出。能复制粘贴执行。

## 交付物
文件清单。
```

写不变量时的自检：**每一条都要能改写成一个 `assert`。** 写不成断言的，是愿望，不是不变量。

## 在别的会话里开工

上下文不共享，只有文件共享。所以新会话只需要三样东西：一张卡片、一个角色、一个交付格式。

### 第一步：说清你是谁

实现者：

```
读 docs/契约/C-001-profile-store.md，按契约实现。
你是实现者：只改「交付物」里列出的文件，其他只读。
先回答「待确认」里的问题，不要猜；答不了就停下来问我。
交付：diff + 验收命令的完整输出 + 未解问题（至少一条）。
```

审查者（盲审，不读实现）：

```
读 docs/契约/C-001-profile-store.md 的「不变量」和「验收」。
你是审查者：不要读 src/ 下的实现，按契约写边界测试。
覆盖：空值、超时、部分失败、重复调用、脏输入。
交付：测试文件 + 你认为实现方最可能搞错的三个点。
```

### 第二步：一次只做一张卡

一个会话一张卡。两张卡同时做，出问题时无法判断是哪张卡引入的。

### 第三步：把结果贴回主会话

主会话（主模型）负责判断 diff 是否越界、断言是否真的覆盖了不变量。**实现者不自评**——这是整套流程里最容易被跳过、也最容易出事的一步。

### 第四步：更新卡片状态

合入后把 `状态` 改成 `已合入`，并在卡片末尾加一行 `合入：<日期> <commit>`。下一张卡片的依赖就靠这个字段接力。

## 与其他文档的关系

- `README.md`：设计事实源，回答"为什么"。
- `HANDOVER.md`：任务清单与风险台账，回答"还剩什么"。
- `docs/分工方案.md`：谁做什么、怎么调用，回答"谁干"。
- 本目录：单个切片的判定标准，回答"做成什么样算对"。

四份文档有冲突时，以「代码 + `npm test`」为准，并在下一次提交里同步修正文档。
